## Context

Telemouse has three machine-readable surfaces an agent can use with no code
changes:

| Surface | Where | What it gives an agent |
|---|---|---|
| ctl JSON API (`127.0.0.1:7880`) | `crates/ctl/src/server.rs`, `manager.rs` | `GET /api/state` (pids, uptime, last 120 log lines, process table), `GET /api/sessions`, `POST /api/components/{capture,viz,doctor,trend,report}/start` with an **allow-listed** flag set, `/stop`, `/marker`, `/processes/{pid}/kill`. Mutations need `X-Telemouse-Ctl: 1`; every call needs a local `Host`. |
| viz HTTP + WS (`127.0.0.1:7879`) | `crates/viz/src/server.rs` | `/healthz`, `/api/stats` (latency percentiles, seq gaps), `/api/sessions` (with the sidecar), `/api/session/{id}` (raw JSONL), `/ws` live batch stream + 1 Hz `viz_stats`. Off-loopback only `/obs`, `/ws`, `/healthz`. |
| analyze CLI + files | `crates/analyze/src/main.rs`, `crates/core/src/recordings.rs` | `list --json`, `report <id> --summary` / `--json` / `--json-dir` / `--csv-dir`, `trend --json`; `<session>.meta.json` sidecar (exit reason, ring drops, per-sink loss); Kafka `mouse.*` topics → Parquet in `tools/kafka2parquet/data`. |

The aim covers four directions (an agent consumes telemouse data, an agent
drives telemouse, agents help develop telemouse, telemouse as a live sensor
for an agent) on three runtimes (Claude Code locally, scheduled cloud
routines, an own Python agent). Rust has no official Anthropic SDK, so any
LLM-calling code lives in Python (the SDK's tool runner) or is delegated to
Claude Code; the Rust side only ever exposes tools.

## Gaps that blocked the good ideas (all closed in step 2)

1. **Programmatic markers.** Markers only came from the F9 hotkey. Now the
   capture agent reads one labelled marker per line from a piped stdin
   (`crates/capture/src/stdin_markers.rs`), the panel starts it with such a
   pipe, and `POST /api/components/capture/marker { label }` writes to it.
2. **Session id → path in analyze.** `report` took a path; it now also takes
   the bare id `list` and the panel show, looked up in `--dir`.
3. **Sidecar in the API.** Viz `/api/sessions` entries carry the parsed
   `<id>.meta.json` as `sidecar`, so "which sessions lost data" is one call.
4. **LLM-sized report.** `report --summary` prints ~3 KB of headline JSON
   (`telemouse-report-summary/1`, `Report::summary()`), a projection of the
   full report plus the sidecar's per-sink losses.
5. **The JSON shapes in one place.** [API.md](API.md).

## Remote

Everything above assumes the agent runs on the machine that captures. That
is the right default: ctl can terminate processes and viz streams every
mouse movement, and their whole security model is "loopback plus a `Host`
check plus one header". None of that survives a network. So the remote
option is a design rule, not a config flag:

**Remote agents talk to `telemouse-mcp`, never to ctl or viz.** The MCP
server stays the only thing that gets exposed, and it is the place where
authentication, an allow-list of tools, and rate limits live. ctl and viz
keep their loopback bind and their trust rule unchanged.

What that takes, in order:

1. **A second transport on the MCP server.** Stdio for local Claude Code,
   plus streamable HTTP (`[mcp] http_addr`, off by default) for anything
   remote. Same tool set, same code: the transport is the last two lines of
   `crates/mcp/src/main.rs` and no tool body knows about it, so this is
   rmcp's `transport-streamable-http-server` feature, two config keys and a
   `StreamableHttpService` beside `stdio()`.
2. **A bearer token.** `[mcp] token` (or a token file next to
   `telemouse.toml`), required on every HTTP request, compared in constant
   time, never logged. No token configured means the HTTP transport
   refuses to start. This is enough for a single user; there is no reason
   to build accounts.
3. **Transport security from a tunnel, not from telemouse.** Tailscale
   (bind the HTTP transport to the tailnet address), Cloudflare Tunnel, or
   an SSH forward. Telemouse never terminates TLS and never listens on a
   public address. The same firewall-rule caveat as the LAN OBS overlay
   applies: bind to a specific interface, not `0.0.0.0`.
4. **A remote tool profile.** Read-only tools (`sessions_list`,
   `session_summary`, `trend`, `health`, `logs_tail`, `live_stats`) are
   available remotely by default; control tools (`capture_start`,
   `capture_stop`, `marker`) need `[mcp] remote_control = true`; `kill` is
   never remote. The mechanism already exists as `--read-only`
   (`server::CONTROL_TOOLS` removed from that instance's router, which is
   why `#[tool_handler]` is given `router = self.tool_router`); a remote
   profile is a third set, built the same way. The server logs every remote
   call with the tool name and the caller's address — the per-call line
   behind the `observability` feature is already that line minus the
   address.

What it unlocks:

- **Cloud routines and Managed Agents** can reach the tools directly: the
  Messages API's MCP connector and a Managed Agent's MCP toolset take an
  HTTP MCP URL, so A5 (log health), C2 (perf gate) and a weekly A4 summary
  can run on a schedule without a local scheduler.
- **Claude Code on another machine** (a laptop, the web app) can drive an
  experiment on the gaming PC: start, mark, stop, summarize.
- **A Python agent off-box** for B2 and D1 without shipping recordings
  around; only the summaries cross the network. D1's live feature stream
  is the one case that needs the raw `/ws` feed; that consumer runs on the
  capture machine and publishes features, not events.

Data can also go remote without any of the above: Kafka already ships every
envelope off the box, and `tools/kafka2parquet` turns it into Parquet. A
cloud routine that reads that Parquet from object storage covers the
consume-only ideas (A4, most of A5) with nothing exposed at all. That is
the cheaper path for anything that does not need to *drive* capture.

Not in scope: exposing the viz dashboard or the panel page remotely
(use a tunnel to the whole machine if you want that), multi-user access,
and any form of remote binary or config update.

## How step 2 was verified

- Piped two lines into a 4-second `telemouse run` with a scratch config;
  both markers appear in the recording with their labels and in
  `report --json` under `markers[]`.
- Drove a second session through the panel API: start, two markers, a
  blank label (400), a call without the guard header (403), a graceful
  stop, a marker after the stop (409). Both markers are in the JSONL.
- `report <id> --summary` on those sessions and on `demo-session` by bare
  id; the summary is ~2.8 KB.
- `cargo fmt --check`, clippy in both feature flavours, `cargo test` with
  and without default features: green. Unit tests added for the stdin
  parser, the label validation, the manager and route error mapping, and
  the sidecar in the viz listing.

## How step 3 was verified

- Piped `initialize`, `notifications/initialized`, `tools/list` and three
  `tools/call` frames into `target\release\telemouse-mcp.exe` and read the
  replies. The handshake answers as `telemouse-mcp 0.2.0` on protocol
  `2025-06-18` with 11 tools; `session_summary` on `demo-session` came back
  as ~3.0 KB of `telemouse-report-summary/1` and `sessions_list` as 735
  bytes. stdout carried exactly the five JSON-RPC replies and nothing else,
  with every log line on stderr and in `logs/mcp.log`. The process exited 0
  on stdin EOF.
- With neither server running, `health` answers rather than failing: both
  halves say `reachable: false` and name the binary, the address and the
  config key to check.
- Unit tests cover the argument allow-lists, the id rule, the `/api/state`
  and `/api/stats` projections, and a canned-response ctl standing in for
  the real one (guard header, `Host`, the `409` relay); one test drives a
  whole MCP session over an in-memory duplex and asserts that a `--read-only`
  server neither lists nor answers a control tool.
- `cargo fmt --check`, clippy in both feature flavours with `crates/mcp`
  added to the minimal line, and `cargo test` with and without default
  features: green.
